## 2. Two things I verified rather than assumed

### 2.1 `hasPrev` is load-bearing — proven, not taken on trust

Joel, Linus, and Kent all said dropping `hasPrev` panics on first deploy. I didn't take it on
authority; I removed the guard and ran the test:

```
--- FAIL: TestDeploy_WarnsWhenCompressionReEnabledOnRedeploy/first_deploy_has_no_previous_config
panic: runtime error: invalid memory address or nil pointer dereference
```

Confirmed at runtime: `prev` is nil on first deploy, `&&` short-circuits, the guard is required and
must stay first. Guard restored; green. Recording the empirical result so the next person who thinks
that first term looks redundant has a panic trace instead of an argument.

### 2.2 The emitted bytes — I read the real file, not just the assertions

`Contains` assertions can pass on a structurally broken file. I generated a Caddyfile from a
two-service registry (alpha: 2 hostnames, default; streamy: 1 hostname, opted out) via a temporary
test, read it, and **deleted the temp test** (`git status` confirms it's gone):

```
# Caddyfile generated by decloud — do not edit by hand.
# Re-run `decloud caddy reload` to refresh.

{
    servers {
        protocols h1 h2
    }
}

alpha.example.com {
    encode zstd gzip
    reverse_proxy decloud-alpha:8080
}
www.alpha.example.com {
    encode zstd gzip
    reverse_proxy decloud-alpha:8080

streamy.example.com {
```

Every property the plan asked for, visible at once: `encode` in **both** of alpha's blocks (inner
loop correct), absent from streamy's block **which keeps its `reverse_proxy`**, absent from the
global options block, 4-space indent, `encode` before `reverse_proxy`.

**This is byte evidence, not validation.** It does not prove Caddy accepts it — that's
`service.go:413` on the operator's host.

Both reviews **APPROVED**. Linus: "Required: nothing." Kevlin: one nit — the duplicated

**Action taken: dropped the CLI-site comment** (`internal/cli/deploy_service.go`), kept the
`deploy.Request` field one. Kevlin's reasoning is the same as my own instinct and is correct: the
CLI-site comment annotated `DisableCompression: f.NoCompression` — a line whose meaning is complete

declaration.

Nothing else changed. Linus's test-14 gap is Kent's, in `internal/deploy/service_test.go` — untouched
by me. Docs are Raymond's — untouched by me.

**One thing worth recording, because it nearly slipped through.** Removing the comment merged the
`deploy.Request` literal back into a single gofmt alignment group, so **every field in it needed
re-alignment** — the change was not the one-line deletion it looked like. My first verification pass
printed "gofmt clean" while `gofmt -l` was in fact **listing the file**: `gofmt -l` exits 0 whether or
not it reports anything, so an `&&` chain reads as success on unformatted code. I caught it only
because I printed the list. **`gofmt -l` in a CI-style `&&` chain is a false green** — test emptiness
of its output, not its exit code. Re-verified with an explicit emptiness check:

- `gofmt -l internal/` — **empty**. `go build ./...` ok. `go vet ./...` ok.
- `go test ./...` — **green, all packages.** Zero regressions.

**Production line count is unchanged at 8 outside the CLI** (the deletion was a comment, which the
tripwire never counted). The CLI drops from 6 to **4**: field 1 + `BoolVar` 2 + mapping 1.
