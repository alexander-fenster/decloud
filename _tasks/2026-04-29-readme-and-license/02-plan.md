## 2. State of the project — the honest read

I traced the repo and the docs side by side. Here is what is actually shipped vs. what is planned, because the README has to reflect the **shipped** surface, not the **roadmap surface**, or it will lie to readers within a milestone.

### 2.1 What ships today (M1 + M2)

Verified by reading `cmd/decloud/main.go`, `internal/cli/root.go`, the per-command files in `internal/cli/`, and `internal/registry/types.go`:

- One binary: `decloud` (`cmd/decloud/main.go`). Module path `github.com/alexander-fenster/decloud` (`go.mod`). Go 1.22+.
- Cobra command tree (`internal/cli/root.go`):
  - `decloud deploy service` (`internal/cli/deploy_service.go`).
  - `decloud unregister`, `start`, `stop`, `restart`, `status`, `logs` (one file each in `internal/cli/`).
  - `decloud caddy {up,down,reload}` (`internal/cli/caddy_*.go`).
- `--mount` is supported on `deploy service` (M2 just landed: commit `2c8aea9`). Bind paths and Docker named volumes both accepted; `:ro` mode flag accepted. Validation matches between the CLI parser and the on-disk loader.
- Caddy runs as a Decloud-managed Docker container `decloud-caddy` on the shared `decloud` Docker network. There is no host Caddy package in the supported install path. (`internal/caddy/manager.go`, `_ai/decisions/caddy-runs-in-container.md`.)
- Deploy strategy is `recreate`. There is brief downtime during the swap. Blue/green is M4.
- Registry layout is the two-file split: `/opt/decloud/config/services/<name>.toml` (mode 0644) and `/opt/decloud/secrets/<name>/env.toml` (mode 0600 in a 0700 dir). Schema version `1`. (`internal/registry/types.go:5,9-26,28-34`.)
- `env.sh` capture works on macOS bash 3.2 and Linux bash 5+ (`internal/envcap/capture.go:37-44`, the `compgen -e` mechanism). No GNU coreutils.
- Exit code surface is the documented eleven-value set (`internal/cli/exit_codes.go:13-23`): 0/2/10/20/30/40/50/60/70/130. The mapping is by typed sentinel via `errors.Is`, not by string matching, plus a small Cobra-usage substring fallback.
- Build-tagged integration test for `--mount` exists (`internal/integration/mount_test.go`, gated on `DECLOUD_INTEGRATION=1` and the `integration` build tag). No CI runs it on this dev machine; the maintainer runs it on a Linux Docker host.

### 2.2 What is NOT shipped (and the README must NOT pretend otherwise)

These are listed in the original `README.md` as if they exist, but they don't:

- **No client binary.** The README's "CLI Shape" section talks about a laptop-side `decloud` client that packages source and pushes over SSH. That is M7 (formerly M3b, deferred per `_tasks/2026-04-28-milestone-resequence/`). For M1+M2 the operator SSHes into the host and runs `decloud` directly. `_docs/usage.md:5-6` says this explicitly.
- **No host bootstrap.** No `decloud bootstrap` subcommand. `_docs/install.md` walks you through manual install (apt-get docker, `mkdir -p /opt/decloud/...`, `go install`, `decloud caddy up`). Bootstrap is M3.
- **No jobs.** No `decloud deploy job`, no systemd timers generated by Decloud, no `--port=0` worker mode (`_ai/decisions/no-magic-zero-modes.md` explicitly forbids that). Jobs are M5.
- **No backups.** No `decloud backup run/list/restore`, no `restic` integration. M6.
- **No image GC.** No `decloud gc`. The README narrative even says "weekly systemd timer runs `docker system prune -a`" — that timer does not exist. M6.
- **No blue/green deploy.** No Caddy admin API path; deploys are recreate-only with a `caddy reload` after the swap. M4.
- **No persistent volumes via named-volume auto-discovery in backups.** Mounts work for runtime (M2), but the backup logic that discovers them does not exist (because backups don't exist).
- **No `decloud` daemon, no listening port for management, no host systemd unit for Decloud itself.** This part the README and code agree on; documenting it for the rewrite.

## 3. README structure — what the new file should contain

The rule: every section answers a question a stranger has. No section exists for completeness theatre.

### 3.1 Section list

Top-to-bottom, the sections I want, with rationale:

1. **`# Decloud`** — H1 plus a one-paragraph elevator pitch. Two sentences max. What it is (single-host PaaS for low-traffic services), what it replaces (Cloud Run / host systemd / Cloud Scheduler at hobby scale). State the audience explicitly: one operator, one VM, SSH access.

2. **Project status** — explicit, prominent, before anyone tries to install: "Decloud is **mid-build**. M1 (server-side service deploy) and M2 (persistent volumes via `--mount`) ship. The client binary, host bootstrap, jobs, blue/green deploys, backups, and image GC are on the roadmap (see [Roadmap](#roadmap))." This is the part the original README fails most badly at — it reads like the whole thing exists.

3. **Quick start** — a copy-pasteable five-step path: SSH to host → `mkdir /opt/decloud/...` (the §4 commands from `install.md`) → `go install` the binary → `decloud caddy up` → `decloud deploy service --name myservice --host myservice.example.com --port 8080 ./myservice`. Pull this from `_docs/install.md` §6 and `_docs/usage.md` §1. Keep it tight; defer details to the docs links.

4. **What you get today (M1 + M2)** — bulleted list of the actually-shipped commands (`deploy service`, `unregister`, `start`, `stop`, `restart`, `status`, `logs`, `caddy up/down/reload`), strategy (`recreate`), volume support (`--mount` for binds and named volumes), env capture model (sourced bash, captured, never baked into image). Each bullet 1 line. This is the README's anti-vaporware section.

5. **Architecture in 60 seconds** — short prose summary of the model: one host, Docker for workloads, `decloud-caddy` container for ingress and TLS, persistent state under `/opt/decloud/`, no listening management port (SSH is the management transport). Distilled from the existing `README.md`'s "Operating Model" section but cut by ~70%.

6. **Install** — short overview plus a link to `_docs/install.md` for the full procedure. Do not duplicate the install doc; the README is not the install manual. Mention the OS target (Linux, Ubuntu LTS / Debian assumed), the prerequisites (Docker, ports 80/443/443-UDP open, DNS already pointed at the host), and the manual-install caveat (no bootstrap script yet — M3).

7. **Usage** — short overview plus a link to `_docs/usage.md`. Three illustrative one-liners (deploy a service, deploy with a mount, check status) so the page is self-contained for the impatient reader. The full flag table lives in `_docs/usage.md`.

8. **Roadmap** — explicit milestone list with what shipped vs. what's planned, sourced from `_ai/decisions/m1-scope.md` and the resequence task (`_tasks/2026-04-28-milestone-resequence/`). Format: short table or labelled list. Honest labels: M1 SHIPPED, M2 SHIPPED, M3 (host bootstrap) PLANNED, M4 (zero-downtime blue/green) PLANNED, M5 (jobs) PLANNED, M6 (backups + image GC) PLANNED, M7 (client binary, secret files, polish) PLANNED. Single sentence per milestone, no detail bloat.

9. **Non-goals** — short bullet list lifted from the existing `README.md`'s "Non-Goals" section. This is one of the few parts of the existing README I want to **keep** as-is in spirit. It tells the reader what Decloud will never do, which is just as load-bearing as the "what it does" section. Trim verbiage; keep the substance.

10. **Repository layout** — one short paragraph or a small tree showing `cmd/`, `internal/`, `_docs/`, `_ai/`, `_tasks/`. Helps a contributor (or a future LLM agent) orient quickly. Do not enumerate every file; just the top-level directories with one-line purposes.

11. **Contributing / development** — short. Build with `go build ./cmd/decloud`, test with `go test ./...`, integration tests gated on `DECLOUD_INTEGRATION=1` and `-tags integration` (see `internal/integration/doc.go`). Code style notes: gofmt, Cobra for flags, Testify+gomock for tests (cite `CLAUDE.md`).

12. **License** — one sentence: "MIT, see [`LICENSE`](./LICENSE)."

## 4. LICENSE file — what to write

Standard MIT license. Two parameters need filling in:

- Year: **2026** (per the harness `currentDate` of `2026-04-29`).
- Copyright holder: **Alexander Fenster** (per `git log` author line and `_docs/install.md`'s `go install github.com/alexander-fenster/decloud/cmd/decloud@latest` path).

The canonical MIT text is the one published by OSI at https://opensource.org/license/mit. No modifications. No "Software" -> "Decloud" substitutions; the OSI text uses `the Software` and that is the form everyone recognizes. Header line is:

```
MIT License

Copyright (c) 2026 Alexander Fenster

Permission is hereby granted, free of charge, ...
```

Followed by the standard four-paragraph body and the all-caps disclaimer paragraph. File mode is whatever git stores by default (0644). File name is `LICENSE` at the repo root, no extension.

I am NOT picking Apache-2.0 even though the implementation-planning v2 plan (`_tasks/2026-04-26-readme-implementation-planning/05-plan-v2.md` §10) said "I lean Apache-2.0 because we may want patent grants." The user explicitly asked for MIT. User wins. If the patent-grant question ever becomes load-bearing the maintainer can re-license; in the meantime MIT matches everyone's expectation for a small Go tool.

- **`_docs/install.md` §8 will go stale the moment LICENSE lands.** Flagged in §2.4 above. Joel's tech plan must include a one-line edit to `install.md` §8 OR explicitly punt it to a follow-up task. Punting is fine if scoped explicitly; silently leaving stale text in `_docs/` is not.
- **The Roadmap section depends on accurate milestone state.** If between this plan and the actual rewrite a new commit changes what's shipped (unlikely in this branch — we are documentation-only), the rewrite has to re-check `git log`. Cheap to do; flag for Raymond.
- **Quick-start commands must work copy-pasted.** That means `go install github.com/alexander-fenster/decloud/cmd/decloud@latest` has to be valid (it is — `go.mod` module path matches), the `mkdir -p /opt/decloud/...` chmod sequence has to be the actually-required modes (it is — verified against `_docs/install.md` §4), and the `decloud deploy service` example has to use real flag names (`--name`, `--host`, `--port`, `--readiness-path`, source dir as positional — verified against `internal/cli/deploy_service.go:57-67`).

- **Year on the LICENSE.** 2026. Do not write 2024 or 2025 because the codebase started in late 2025 — MIT copyright dates are the year the work is published / available, and the repo is publicly available now in 2026. Single year is fine; "2026-present" is unnecessary boilerplate for a project this young.
