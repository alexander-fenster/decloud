# 03 — Joel's Tech Plan: Disable Caddy HTTP/3 (advertise only h1 + h2)

Expands Don's plan (`02-plan.md`). Don's diagnosis is correct and I verified every
load-bearing claim against the actual source on this branch. One of Don's incidental
assumptions — and the task brief's assumption — about Caddyfile indentation is **wrong
for this codebase**, and getting it wrong would produce inconsistent output. That, plus
the exact emitted bytes, is the heart of this spec. Read §3 carefully.

---

## 0. Functional spec (what the system must do)

**Behavior.** When Decloud writes the generated Caddyfile, that file MUST begin with a
Caddy global options block declaring `servers { protocols h1 h2 }`. Caddy reads this
and stops advertising/serving HTTP/3 (QUIC) on all auto-created TLS servers. The user's
symptom (iPhone Safari hanging on broken QUIC/UDP-443 with slow TCP fallback) goes away
because the client is never offered h3 in the first place (no `Alt-Svc: h3=...` header,
no HTTP/3 advertisement in the TLS handshake).

**What the operator sees:** nothing new in the CLI. `decloud caddy reload` (and deploy,
and unregister) regenerate the Caddyfile exactly as before; the only difference is the
four-extra-lines global block at the top of `/opt/decloud/config/caddy/Caddyfile`. An
operator who inspects that file sees the block and understands h3 is off. No new flags,
no new errors, no new exit codes.

**What does NOT change:** the stub (`:80` plaintext), the published port maps (UDP/443
stays published but inert), the reload funnel, the validate/rename/reload sequence, and
every per-site `reverse_proxy host:port` block (byte-identical to today).

**Performance:** irrelevant — this adds ~70 bytes to a file written once per reload.

## 1. Code to leverage (forensic archaeology — verified against source on this branch)

### 1.1 The one and only production change site

`internal/caddy/generator.go`, `func (g *textGenerator) Generate` (lines 35–49).
The function builds the whole file into a `bytes.Buffer` with `fmt.Fprintln`/`Fprintf`
and hands it to `writeFileAtomic`. It already owns byte order for the entire file, so
the global block goes in cleanly. Verified current body:

```go
func (g *textGenerator) Generate(outPath string, services []*registry.Service) error {
	inputs := normalize(services)
	var buf bytes.Buffer
	fmt.Fprintln(&buf, "# Caddyfile generated by decloud — do not edit by hand.")
	fmt.Fprintln(&buf, "# Re-run `decloud caddy reload` to refresh.")
	for _, in := range inputs {
		fmt.Fprintln(&buf)
		for _, host := range in.Hostnames {
			fmt.Fprintf(&buf, "%s {\n", host)
			fmt.Fprintf(&buf, "    reverse_proxy %s:%d\n", in.ContainerName, in.Port)
			fmt.Fprintln(&buf, "}")
		}
	}
	return writeFileAtomic(outPath, buf.Bytes())
}
```

The two header `Fprintln`s are the existing emission pattern to mirror. The per-service
loop opens each block with a leading `fmt.Fprintln(&buf)` (blank-line separator) — that
same separator idiom is what we reuse to put a blank line after the global block.

## 2. The indentation correction (READ THIS — the brief is wrong here)

The task brief and Don's note both say "Caddyfile uses tabs by convention; match
existing generated output." The *first half* is a general Caddy community convention;
the *second half* is the binding instruction, and **the existing generated output uses
4 SPACES, not tabs.** Proven by source and by running the real generator:

- `generator.go:44` emits `"    reverse_proxy %s:%d\n"` — that is four U+0020 spaces.
- `stub.go:11` likewise indents `respond ...` with four spaces.
- Captured real output of the current generator for one service (exact bytes):

  ```
  # Caddyfile generated by decloud — do not edit by hand.\n
  # Re-run `decloud caddy reload` to refresh.\n
  \n
  foo.example.com {\n
      reverse_proxy decloud-foo:8080\n
  }\n
  ```

  (The `    ` before `reverse_proxy` is four spaces.)

**Decision (locked): the global block uses 4-space indentation to match existing
output.** `servers` is indented 4 spaces; `protocols h1 h2` is indented 8 spaces.
Using tabs here would make the generated file mix tabs and spaces, which is ugly and
would fail any `caddyfmt` normalization the operator might run. Consistency with the
file's own existing style beats the external community convention. (Caddy's parser
accepts either; correctness is unaffected, but house style is 4 spaces.)

Note for the implementer: this is *generated text inside a Go string literal*. `gofmt`
governs the `.go` source (the `\n`-and-spaces literal is fine for gofmt). It does NOT
touch the bytes inside the string. So there is no gofmt-vs-Caddyfile tension as long as
you write the spaces as literal spaces in the Go string.

## 3. Exact insertion — the precise bytes

Insert the global block **after** the two header `Fprintln` lines (generator.go:38–39)
and **before** the `for _, in := range inputs` loop (generator.go:40). This makes the
global block the first non-comment block in the file, which Caddy *requires* — the
global options block must precede every site block or `caddy validate` errors.

The implementer (Rob) writes the production code; this spec fixes the exact output
contract. The emitted block, byte-for-byte, MUST be:

```
\n
{\n
    servers {\n
        protocols h1 h2\n
    }\n
}\n
```

That is:
- a leading blank line (`\n`) separating the header comments from the block,
- `{` at column 0,
- `    servers {` (4 spaces),
- `        protocols h1 h2` (8 spaces),
- `    }` (4 spaces) closing `servers`,
- `}` at column 0 closing the global block.

After this block, the existing per-service loop runs unchanged. Because that loop's
first statement is `fmt.Fprintln(&buf)` (a blank line), the resulting separation between
the closing `}` of the global block and the first `host {` line is exactly one blank
line — matching the spacing already used between sites. No extra blank-line handling is
needed; do NOT add a second separator.

**Resulting full output for one service (the new contract — exact bytes):**

```
# Caddyfile generated by decloud — do not edit by hand.\n
# Re-run `decloud caddy reload` to refresh.\n
\n
{\n
    servers {\n
        protocols h1 h2\n
    }\n
}\n
\n
foo.example.com {\n
    reverse_proxy decloud-foo:8080\n
}\n
```

**Resulting full output for empty registry (the new empty contract — exact bytes):**

```
# Caddyfile generated by decloud — do not edit by hand.\n
# Re-run `decloud caddy reload` to refresh.\n
\n
{\n
    servers {\n
        protocols h1 h2\n
    }\n
}\n
```

(Header, blank line, global block — and nothing else. No trailing site blocks, no
`reverse_proxy`.)

**Implementation hint (non-binding — Rob owns the code):** the cleanest mirror of the
existing style is a small run of `fmt.Fprintln(&buf, ...)` calls inserted between
lines 39 and 40, e.g. one blank `Fprintln`, then the six literal lines above. A single
multi-line raw-string `Fprint` is equally acceptable as long as the emitted bytes match
this spec exactly (including the four/eight-space indentation and the trailing `\n`s).
Whatever form Rob picks, the test in §4.1 is the arbiter.

## 4. Tests (Kent owns authoring; this is the spec)

All in `internal/caddy/generator_test.go`, using the existing helpers from §1.2.

### 4.1 NEW: `TestGenerator_DisablesHTTP3` (the core regression test)

Generate with one service (`makeService("foo", 8080, "foo.example.com")`), read the
body, and assert:

1. `assert.Contains(t, body, "protocols h1 h2")` — the directive is present.
2. **No HTTP/3 on the `protocols` line — scoped, NOT a whole-file `NotContains`.** A bare
   `assert.NotContains(t, body, "h3")` false-positives the day a fixture hostname contains
   the literal `h3` (e.g. `h3.example.com`) — see §6.5. Do NOT use it. Instead, scope the
   negative assertion to the exact directive line, so it can never collide with a hostname:
   ```go
   assert.Contains(t, body, "protocols h1 h2\n", "protocols line must advertise exactly h1 h2")
   assert.NotContains(t, body, "protocols h1 h2 h3", "h3 must not be on the protocols line")
   assert.NotContains(t, body, "h1 h2 h3", "no h3 anywhere on the protocols directive")
   ```
   The positive `"protocols h1 h2\n"` assertion is the real contract: it pins the directive
   to terminate at `h2` immediately before the newline, so any trailing ` h3` (or any other
   protocol) would break it. The two `NotContains` calls are belt-and-suspenders against an
   `h3` re-introduction. None of these three can be tripped by a hostname like
   `h3.example.com`, because all three match against the literal `protocols`/`h1 h2`
   directive text, not a bare `h3` substring. This removes the §6.5 fixture-discipline trap
   entirely — robustness by construction, not by convention.
3. `assert.Contains(t, body, "servers {")` — the wrapping block is present.
4. **Ordering (correctness, not cosmetics):** the global block MUST precede the first
   site block. Mirror the `strings.Index` pattern from `TestGenerator_MultiServiceMultiHostSorted`:
   ```go
   protoIdx := strings.Index(body, "protocols h1 h2")
   siteIdx := strings.Index(body, "foo.example.com {")
   require.GreaterOrEqual(t, protoIdx, 0)
   require.GreaterOrEqual(t, siteIdx, 0)
   assert.Less(t, protoIdx, siteIdx, "global options block must precede site blocks")
   ```
   This guards the Caddy "global block must be first" rule that we cannot verify with a
   real `caddy validate` here (see §6).

Recommended additionally (cheap, high value): assert the exact indentation is present,
e.g. `assert.Contains(t, body, "\n    servers {\n")` and
`assert.Contains(t, body, "\n        protocols h1 h2\n")`. This locks the 4/8-space house
style from §2 so a future tab-vs-space regression is caught. This is a deliberate
style-contract assertion, acceptable under the no-change-detector rule because mixed
indentation is a real defect we are choosing to prevent.

## 5. Resolving Don's three open questions (firm decisions)

### 5.1 Emit the global block on empty registry? — YES. LOCKED.

Rationale: (a) keeps the generator's output shape invariant — the protocols guarantee
holds the instant the first service appears, with no "first deploy still advertises h3"
window; (b) a global options block with zero site blocks is valid Caddyfile syntax and
inert; (c) it makes the contract trivially testable (§4.2). Cost: one existing test
updates (§4.2), which is legitimate because the contract genuinely changed. **Decision:
always emit, unconditionally, exactly once.**

### 5.2 Add the block to the stub (`:80`)? — NO. LOCKED.

The stub is `:80` plaintext (`stub.go:10–14`). HTTP/3 requires TLS; it cannot exist on a
plaintext `:80` server, so the block would be functionally inert there. Adding it buys
zero protocol behavior and forces a `stub_test.go` edit for cosmetics. The stub is also
*replaced* by the generated file the moment any service with a hostname is registered;
real TLS traffic only ever hits the generator's output. **Decision: leave `stub.go`
exactly as-is.** (If a future task wants global-options uniformity across both producers,
that is a cosmetic follow-up, not this bug fix.)

### 5.3 Also unpublish UDP/443 in `runOpts()`? — NO, NOT IN THIS TASK. LOCKED.

`manager.go` `runOpts()` (lines 124–145) publishes the dual-stack UDP/443 maps. Once h3
is disabled in the Caddyfile, nothing inside the container listens on UDP/443, so the
published port is inert (packets arrive at a closed in-container port; harmless). Removing
the port maps:
- requires a **container recreate** (`decloud caddy up`), not the cheap `caddy reload`
  this task rides on — a strictly larger blast radius;
- touches the documented dual-stack publishing decision (`caddy-runs-in-container.md:17,47`)
  in a way that affects `caddy up` semantics;
- is **not required** to satisfy the request — disabling h3 in the Caddyfile fully stops
  the advertisement and serving of HTTP/3, which is exactly and only what the user asked.

**Decision: leave the port maps untouched.** File a follow-up task *if* the operator
later wants UDP/443 closed for firewall-surface reasons. The amended decision record
(§7) MUST state that UDP/443 remains published-but-inert so the next engineer isn't
confused by an open port with no listener.

## 6. Gotchas and landmines

1. **Global block MUST be first.** Caddy rejects a Caddyfile where the global options
   block appears after any site block. Our insertion point (after header comments,
   before the service loop) satisfies this. The §4.1 ordering assertion is the guard.
   Do not let any future refactor move site emission above the global block.

2. **Indentation: 4 spaces, NOT tabs.** See §2. The single most likely implementation
   error is copying a tab-indented Caddyfile snippet from Caddy's docs. That would mix
   tabs and spaces in the output. The §4.1 indentation assertions catch it.

3. **Exactly one blank line between the global block and the first site.** The service
   loop already emits a leading `fmt.Fprintln(&buf)`. If the implementer *also* appends
   a trailing blank line after the global block, the file gets a double blank line. Don't.
   Emit the block ending in a single `}\n` and let the loop's existing separator do the
   spacing. The exact-bytes contract in §3 is the arbiter.

4. **No `caddy validate` here — no Docker on this dev box** (MEMORY: "No Docker on this
   Mac"). The unit tests assert on emitted bytes only. The byte-level "block is first +
   well-formed + 4-space-indented + no h3" assertions are our **proxy**, not proof. The
   real `caddy validate` and the real iPhone-Safari-over-real-network check are a manual
   integration step the maintainer runs on the Linux host. **Rob and Raymond must not
   write the word "validated" anywhere** — say "byte-asserted; pending operator
   `caddy validate`."

5. **No whole-file `NotContains(body, "h3")` — scope the negative to the `protocols`
   line.** A bare `assert.NotContains(t, body, "h3")` false-positives the day any fixture
   hostname contains the literal `h3` (e.g. `h3.example.com`), failing for the wrong reason
   and training people to "just edit the test." We do NOT rely on fixture discipline (that
   was the earlier, rejected approach). §4.1 instead asserts the positive contract
   (`"protocols h1 h2\n"` present) plus narrow negatives scoped to the directive text
   (`NotContains "protocols h1 h2 h3"`, `NotContains "h1 h2 h3"`). These match the literal
   `protocols`/`h1 h2` directive, never a bare `h3`, so a hostname containing `h3` cannot
   trip them. Robustness is by construction, not by a fixture-keep-clean comment. Kent: use
   the §4.1 assertions exactly; do NOT add a whole-file `NotContains "h3"`.

6. **Leaky abstraction (Spolsky's law):** the generator pretends to be "just emit site
   blocks," but Caddyfile global semantics (must-be-first ordering, global-vs-site
   directive scope) leak through. We document the ordering requirement in code review and
   in the §4.1 test so the leak is contained.
